# ClawBridge AI Reaches Best-in-Class Quality Through Host-Enforced Primitives

None of the products studied has a better model than ClawBridge can run. What separates best-in-class quality from an ordinary Slack bot is a small set of harness primitives, and ClawBridge's host has to enforce every one of them rather than leave them to the model's judgment. The first is a cache-stable, append-only thread fed by a fixed set of tools, with integrations exposed as code. The reference product reports an **81.8% cost cut per 40-call thread and 93–96% cache hits on Claude** this way (reference-product research, private notes). The second is memory that is scoped by who said it and where, stamped on write and filtered on read. The third is drafts that wait behind Approve/Reject buttons only the requester can press. The fourth is condition scripts that decide whether the model wakes at all. The fifth is a benchmark that rewards staying silent and catches leaks. Each competitor gets one piece of this right. Grok Bot has the best identity, credential and approval model. getdot.ai's Dot has the best curated, reviewed memory and golden-answer evals. OpenClaw has the deepest Slack adapter, NanoClaw the strictest container and credential isolation, and Hermes the most complete self-improvement loop. None of them ships host-enforced multi-user scoping, and the open-source harnesses have long-standing open issues asking for it. That gap is where the agent can win. The decision with the biggest consequences, though, is about Slack distribution rather than the harness. If each install ships as an **internal app the customer creates from a manifest**, it keeps full history rate limits, Real-time Search and the Slack MCP server. A single ClawBridge-owned app distributed without a Marketplace listing is held to **1 history request per minute at 15 messages**, with no RTS and no MCP ([Slack](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps/)). Separately, ClawBridge has to move to Slack's new `agent_view` before `assistant_view` is deprecated in February 2027 ([Slack](https://docs.slack.dev/changelog/2026/08/20/agent-updates/)).

## Each product gets one piece of the harness right, and none gets all of them

The field splits into hosted "coworker" products and open-source harnesses. They put the agent in different places. Grok Bot is a desktop and mobile "Bots with a computer" app, and its Slack presence is a projection of shared Bots: each shared Bot gets its own Slack app and handle, and every teammate must link their Slack account before it will serve them ([xAI docs](https://docs.x.ai/grok-bot/team-bots)). getdot.ai's Dot is a team data analyst. It is mention-first and thread-scoped, it never reads channel traffic it wasn't invoked in, and an admin chooses which channels it answers in ([getdot docs](https://docs.getdot.ai/integrations/slack-and-teams/slack)). OpenAI's dots, launched 29 September 2026, are personal agents that happen to post in Slack. Per the help-center text quoted by a third party, "only you (the owner) can ask your dot to do things" ([geniusly.ai](https://geniusly.ai/blog/openai-dots-in-slack-limits-and-alternatives-for-teams)). The reference product sits at the opposite pole: one shared employee for the whole workspace, with workspace-owned context, and a positioning page that presents this as its advantage over Grok Bot (reference-product research, private notes).

The open-source landscape is lopsided. **OpenClaw (394k stars) and Hermes (261k)** release almost daily, but both were designed for a single tenant. Hermes's own tracker says "Memory operations bypass the hook system entirely, making tenant isolation impossible without forking core" ([Hermes #34352](https://github.com/NousResearch/hermes-agent/issues/34352)). Another issue notes that sharing a Hermes agent means "giving full access to everything — including `terminal`" ([Hermes #527](https://github.com/NousResearch/hermes-agent/issues/527)). The projects actually built as Slack coworkers are tiny. Kortny has 5 stars and Tag by Hover has 10 ([Kortny](https://github.com/matangilabs/kortny); [hover-tag](https://github.com/klovr-co/hover-tag)). So nothing exists to adopt wholesale, and the multi-user layer ClawBridge needs is the one nobody has built cleanly. NanoClaw, ClawBridge's ancestor, warns about the problem directly: "If different people are involved → separate agent groups. Information will cross-pollinate through agent memory if you don't" ([NanoClaw](https://github.com/nanocoai/nanoclaw/blob/main/docs/isolation-model.md)). The reference product's approach to that warning is host-side scoping, not separate agents, and the agent has to take the same route. One housekeeping item: NanoClaw moved to `nanocoai/nanoclaw` and is on v2 release candidates with a migration script, so ClawBridge should confirm which line its fork tracks.

Two models of ownership compete. Grok Bot is private by default: "Each person's chat is private. The owner and Managers can't read your chats". The Bot also "can save team-wide knowledge and says when it does" ([xAI docs](https://docs.x.ai/grok-bot/team-bots)). The reference product shares by default, so one person's teaching helps the whole team (reference-product research, private notes). Grok's model is safer. The reference product's model compounds learning faster, which is the "feels like a coworker" effect. The evidence points to a synthesis: shared memory as the product, with Grok's privacy guarantees enforced at the boundary, and Dot's rule that shared knowledge changes only through a human-approved diff, because "Dot suggests. People decide" ([getdot docs](https://docs.getdot.ai/train-dot/context-agent.md)). The reference product's own team has said in public that weak permission boundaries cost them a real data-leakage incident with an e-commerce customer (conference talk summary, private notes).

## Slack's 2026 platform rewards internal apps and penalises unlisted ones

### The distribution choice decides what the agent can read

Since 29 May 2025, `conversations.history` and `conversations.replies` for commercially distributed apps without a Marketplace listing have been capped at **Tier 1: one request per minute, with at most 15 objects**. Marketplace apps and internal, customer-built apps are exempt ([Slack](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps/)). The 2026 agent APIs draw the same line. The Real-time Search API (`assistant.search.context`) replaced the Data Access API on 17 February 2026, and it and the Slack MCP server are open **only to Marketplace-published or internal apps; unlisted distributed apps are not allowed** ([RTS guide](https://docs.slack.dev/apis/web-api/real-time-search-api/); [Slack MCP](https://docs.slack.dev/ai/slack-mcp-server)). For a self-hosted product the answer is clear. Each ClawBridge install should create its own Slack app from a manifest in the customer's workspace. NanoClaw already does this, "manifest, avatar, and workspace install, no tokens to paste" ([NanoClaw](https://github.com/nanocoai/nanoclaw)). That app is internal. It keeps 50+ requests per minute and 1,000 objects of history, and it is eligible for RTS and MCP. There is a catch. The same API Terms update calls the Marketplace "the only appropriate channel" for commercially distributing Slack apps, explicitly "including unlisted apps and templated custom apps". So if Mark ever sells a hosted ClawBridge that installs one shared app across many customers, a Marketplace listing is the only compliant path. Its requirements: a public privacy policy, disclosure of LLM data handling, no training on Slack data, prompt deletion on uninstall, and an inaccuracy disclaimer ([Slack Marketplace guidelines](https://docs.slack.dev/slack-marketplace/slack-marketplace-app-guidelines-and-requirements/)). One factual point is unresolved. Slack's changelog says existing unlisted installs are "not affected", while several third-party posts report they were throttled from 3 March 2026 ([dev.to](https://dev.to/helen_mireille_47b02db70c/slack-just-throttled-your-openclaw-agent-you-probably-havent-noticed-yet-d4)). That conflict doesn't change the recommendation.

Distribution also decides transport. Socket Mode needs no public URL, which suits a self-hosted internal app. But Vercel's chat-sdk, which ClawBridge's Slack adapter is built on, **throws if Socket Mode is combined with multi-workspace OAuth credentials** ([chat-sdk](https://chat-sdk.dev/adapters/official/slack)). OpenHands' enterprise docs show the cost of getting this wrong: air-gapped installs are unsupported because Slack webhooks need public IPs ([OpenHands](https://docs.openhands.dev/enterprise/integrations/slack)). Socket Mode for the single-workspace internal app, and the HTTP Events API only for a future Marketplace build, keeps both paths open. On personas, the evidence favours **one agent app per workspace** over Grok's and NanoClaw's one-app-per-agent model. Every extra app needs its own admin approval, and best-in-class quality depends on a single coworker accumulating shared context. Per-agent containers can sit behind one Slack identity. `chat.startStream` accepts `username` and `icon_url` overrides if sub-personas are ever needed ([Slack](https://docs.slack.dev/reference/methods/chat.startStream/)); whether `chat:write.customize` covers `chat.postMessage` was not verified.

### Agent View, streaming and search come with hard limits

The `agent_view` messaging experience shipped on 20 August 2026. It replaces `assistant.threads.setStatus` with `agents.sessions.setStatus`, adds a native stop button, and emits an `agent_session_stopped` event ([Slack](https://docs.slack.dev/changelog/2026/08/20/agent-updates/)). Three details will catch out a naive port. A session in `processing` times out after one hour, and the status **does not clear automatically after a post**, so the harness must set `active` when it finishes, or `suspended` while it waits on an approval ([Slack](https://docs.slack.dev/ai/developing-ai-apps)). Under `agent_view` in DMs, Slack threads each user message separately, so channel history returns only the user's side and the harness must keep its own transcript ([chat-sdk](https://chat-sdk.dev/adapters/official/slack)). And one third-party report says `setStatus` fails unless the app subscribes to `agent_session_stopped` ([KiroCrew #9822](https://github.com/kirodotdev/KiroCrew/issues/9822)). Native streaming has its own limits. Streams in channels must be thread replies and need `recipient_user_id`/`recipient_team_id`. A stream allows 12,000 characters of markdown, 50 tasks, and **a 10-minute hard lifetime that appends don't extend**, and unfurls are disabled while streaming ([Slack](https://docs.slack.dev/reference/methods/chat.startStream/)). chat-sdk documents rotation at about five minutes, which conflicts with Slack's figure ([chat-sdk](https://chat-sdk.dev/adapters/official/slack)). Long agent tasks therefore need stream rotation: stop with `session_status: processing`, then start a new stream in the same thread.

Search has its own visibility rules. A bot-token RTS query works only inside the Slack client and needs the `action_token` from the triggering event. Private, DM and group-DM search needs **user tokens with per-user consent**. Results depend on where the query runs: a public channel sees only public channels, and a Slack Connect channel sees only itself ([RTS guide](https://docs.slack.dev/apis/web-api/real-time-search-api/)). Semantic search needs Business+ or Enterprise+, and **workspace guests cannot use apps with platform AI features** at all. The data rules forbid storing RTS results, training on them, or sharing one user's authorization with another. All of this fits the reference product's self-described practice: "I keep no copy of Slack messages; I read them live", and "I never claim to have searched private channels or DMs unless it says it had that access" (reference-product self-description, private notes). The agent should search live through RTS, store permalinks rather than content, and report which conversation types each search actually covered. Telegram, WhatsApp and Signal are the exception. Their bots can't fetch history later, so ClawBridge still needs a host-side archive for those channels ([ClawBridge AI spec](../product-spec.md)).

### The behaviours that make an agent feel like a colleague converge across products

On the basic interaction pattern, the products agree to a striking degree. A mention starts a thread, the thread is the session, and follow-ups in that thread need no re-mention. This holds for Grok Bot, Dot, Hermes and OpenHands ([xAI](https://docs.x.ai/grok-bot/team-bots); [getdot](https://docs.getdot.ai/integrations/slack-and-teams/slack); [Hermes](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/slack.md); [OpenHands](https://docs.openhands.dev/openhands/usage/cloud/slack-installation)). OpenClaw spells out the mechanics most fully. Sessions are keyed `agent:<id>:slack:channel:<C>` with a `:thread:<ts>` suffix. The `app_mention` root is seeded into the thread session along with **the 20 most recent existing messages**, and the root text survives compaction. `implicitMentions.replyToBot` and `threadParticipation` let follow-ups skip the mention. A 👀 ack reaction confirms receipt. `progress` streaming renders a native task card, raw command text is hidden by default, and Slack Agent View is supported ([OpenClaw](https://github.com/openclaw/openclaw/blob/main/docs/channels/slack/threads-and-sessions.md); [OpenClaw messaging](https://github.com/openclaw/openclaw/blob/main/docs/channels/slack/messaging.md)). Slack blocks native slash commands inside thread replies, so Hermes accepts `!stop`, `!model` and `!approve` as message prefixes ([Hermes](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/slack.md)). Dot's `!f`/`!e` prefixes and "ultrathink" trigger set the reasoning effort per message, and a progress header shows the current mode ([getdot](https://docs.getdot.ai/using-dot/energy-modes.md)). That maps directly onto Claude Agent SDK and Codex effort settings.

The quality layer above that is what the reference product describes and the others mostly lack. The reference product says its send tool has an explicit "don't send" option, so silence is a deliberate, recorded choice. It sends one status line first and edits a single progress message (task cards, or a ○ ▸ ✓ × checklist where cards aren't available), then posts the result as a *new* message so the notification fires. It writes `@Full Name` mentions and refuses ambiguous first names. And it offers one proactive suggestion at a time, at the end of a useful reply (reference-product self-description, private notes). These are self-reported, so treat them as design targets, not verified behaviour. Grok adds two accountability features worth copying. "The Bot records who requested each message, so anyone in the thread can ask who asked for it". And its guidance: don't rely on emoji reactions for safety-critical decisions ([xAI](https://docs.x.ai/grok-bot/chat-and-collaboration)). The ClawBridge spec's 30-second quiet window before answering unmentioned thread replies needs `message.channels`/`message.groups` subscriptions and a per-thread debounce that is cancelled on new input. chat-sdk's per-installation locks and turn cancellation are the natural place to build it ([chat-sdk](https://chat-sdk.dev/adapters/official/slack)).

## Memory must be scoped by the host on write and on read

The memory systems surveyed (Hindsight, mem0, Zep/Graphiti, Letta, LangMem, Cognee, Supermemory, and the file-based designs) all partition by some identifier. None of them natively understands "a DM versus a public channel". Graphiti's README is blunt about it: on its reference servers "Any caller can read, change, or delete data in any `group_id`" ([Graphiti](https://github.com/getzep/graphiti)). The host therefore has to compute the allowed scope and pass it into every call. The model must never choose who can see a memory. ClawBridge's current Hindsight backend is a defensible choice. It is MIT-licensed, needs only Postgres and pgvector, and has the richest filters found: tags with `tags_match` and nested `tag_groups` ([Hindsight](https://github.com/vectorize-io/hindsight)). It also has two defaults that would leak. **The `any` and `all` match modes return untagged memories; only the strict modes exclude them** ([Hindsight recall](https://hindsight.vectorize.io/developer/api/recall)). And the default `observation_scopes: combined` should be checked before it is allowed to consolidate mixed-visibility evidence into one public belief ([Hindsight retain](https://hindsight.vectorize.io/developer/api/retain)). Private material should therefore sit in hard partitions: separate banks per DM person and per private channel. Tags handle finer topic scoping inside a boundary, and every recall uses strict matching.

The rule that ties this together is an intersection. The readable set for a turn is what the **asker** may see *and* what the **destination surface** may show. In #general, even the asker's own DM notes are excluded. The reference product describes the same rule from the inside: a finance figure one teammate gave in a DM is never used when another teammate asks in #general (reference-product self-description, private notes). Grok applies the same logic to compute and credentials. In your own DM a shared Bot runs on your computer with your signed-in sites. In channels it uses a shared computer and only the owner's apps, and "One person's connection is never used for someone else" ([xAI](https://docs.x.ai/grok-bot/team-bots)). There is also a taint rule. Anything retained from a turn that drew on private memory inherits the private scope, so a summary can't launder a DM fact into public memory. And runs with no person behind them, such as crons and webhooks, never read DMs.

On the write path, the products that learn well separate cheap automatic capture from deliberate curation. Hermes caps `MEMORY.md` at **2,200 characters** and `USER.md` at 1,375. It injects both as a frozen snapshot at session start to keep the prefix cache intact, and returns an error rather than auto-compacting when a write goes over the cap. That forces curation. Its docs also name the most common failure: "a sentence like 'I've added that to my memory' is just text", meaning the save never happened because no tool was called ([Hermes memory](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/memory.md)). OpenClaw excludes files with untrusted provenance from automatic context. Its "dreaming" pass promotes daily notes into `MEMORY.md` only after score, recall-frequency and diversity gates ([OpenClaw memory](https://docs.openclaw.ai/concepts/memory)). Dot routes every in-chat correction and "remember this" into a Proposals inbox as a diff, which admins merge into a git-backed model with dev environments ([getdot](https://docs.getdot.ai/train-dot/context-agent.md)). Letta Code tracks all context in git ([Letta Code](https://github.com/letta-ai/letta-code)). For a workspace where any member's message could try to poison shared memory, the combination is clear. The host stamps visibility. Personal and channel notes are writable directly. Workspace-wide facts change only through an approved diff, and the agent announces when it saves team knowledge, as Grok does.

Freshness is the other half. The reference product's blog frames the real failure as "remembering the wrong thing confidently" ([ClawBridge AI spec](../product-spec.md)). Graphiti's bi-temporal model gives the cleanest fix. Every fact records when it was true and when it was learned, and contradicted facts are invalidated rather than deleted ([Zep paper](https://arxiv.org/html/2501.13956v1)). The cheap version for the agent renders every recalled fact as "fact (as of date, source)" and marks superseded facts invalid rather than deleting them. mem0 moved to ADD-only extraction in April 2026, so its store holds contradictions side by side, and freshness becomes a retrieval-ranking problem ([mem0](https://github.com/mem0ai/mem0)). Dot adds a cheap observability idea. **Full logs → Lineage** shows which notes were loaded versus actually used, so notes that load often but are rarely used can be retired ([getdot](https://docs.getdot.ai/train-dot/maintaining-dot.md)).

Memory leaderboards are not a sound basis for choosing a backend. An audit of LoCoMo found **99 score-corrupting errors in 1,540 questions (about 6.4%)**, and its gpt-4o-mini judge accepted **62.81% of intentionally wrong but topically adjacent answers** ([Penfield Labs](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)). mem0's claimed 92.5 sits within a point of that ceiling ([mem0](https://github.com/mem0ai/mem0)). No public benchmark tests multi-user leak resistance, so ClawBridge has to write its own. Two things remain unconfirmed: Hindsight's per-bank overhead, and whether it supports merged recall across banks. If either fails, ClawBridge must fan out across banks itself.

## Credentials, approvals and schedules belong in one host broker

### Tools as code shrink the prompt and create a choke point

Cloudflare and Anthropic published the same pattern independently in late 2025. The model gets one small tool that executes code, integrations appear as typed functions, and intermediate data stays in the sandbox. Anthropic reports one workflow falling from **about 150,000 to about 2,000 tokens (98.7%)** ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)). In Cloudflare's version, MCP servers become bindings whose supervisor attaches the keys, "so the generated code never handles keys", and global `fetch()` throws ([Cloudflare](https://blog.cloudflare.com/code-mode/)). The reference product's motive was caching more than token count. Its 9,800+ tools are Python functions behind "a small, fixed set of native tools", because dynamically loading tool schemas changes the prefix and breaks the cache (reference-product research, private notes). Hermes ran into the same schema-cost problem (issue #6839) and added RPC-callable tools from scripts ([Hermes](https://github.com/NousResearch/hermes-agent)).

For ClawBridge the argument is architectural as well as economic. If ClawBridge generates a TypeScript module tree from each MCP server's `tools/list` (Bun is already in the runner), and each stub is a thin RPC to a host broker, then every integration call crosses a single host process. That process can hold credentials, apply approval policy per function, tokenize PII, and write an audit row that is complete by construction. The model's tool list shrinks to shell, files, send-message, remember, draft and schedule, and stays byte-identical across users and sessions. Breadth can come from a connector platform behind the broker, as Grok does with Composio and Kortny does natively ([Composio](https://composio.dev/content/guide-to-frok-bot); [Kortny](https://github.com/matangilabs/kortny)). Code mode has a known cost: it means running model-written code, which requires a real sandbox ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)).

### Containers isolate code but do not protect secrets

Two lessons recur across the sources: plain Docker is a weak boundary for model-written code, and the boundary doesn't matter if the secret sits inside it. The usual guidance is gVisor at minimum for LLM-generated code, and Firecracker or Kata microVMs for multi-tenant or hostile workloads ([Northflank](https://northflank.com/blog/kata-containers-vs-firecracker-vs-gvisor)). E2B is the main self-hostable Firecracker platform (Apache-2.0, Linux and KVM only). Daytona's open repository was **archived on 3 October 2026** after development moved private, so new self-hosted work should not depend on it ([Daytona](https://github.com/daytonaio/daytona)). Grok runs every Bot as a non-root user on a persistent VM. Even so, its docs say separate Bots on one person's computer should not be treated as a security boundary ([eesel](https://www.eesel.ai/blog/grok-bot)).

The more important threats are already documented against ClawBridge's own ancestor. NanoClaw issue #865 found that the bash-sanitising hook runs inside the container, where "The agent can rewrite" it. It also found that in OAuth mode the credential proxy let a real temporary API key back into the container. The proposed fixes are to move hard enforcement to the host, inject credentials on every request, and give the container only a placeholder ([NanoClaw #865](https://github.com/nanocoai/nanoclaw/issues/865)). Anthropic's Managed Agents vaults formalise that pattern. The sandbox holds an "opaque placeholder", and the real secret is substituted only into outbound HTTPS requests to that credential's allowed hosts. The docs warn that unrestricted credential networking swaps the secret into requests to *any* reachable host, and advise never giving the agent a Claude API key ([Managed Agents](https://platform.claude.com/docs/en/managed-agents/secure-deployment)). The Claude Agent SDK adds a related caveat: path deny rules such as `Edit(//secrets/**)` don't stop "a script that Claude runs and that opens files itself" ([Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)). Once credentials are host-side, the remaining threat is exfiltration through allowed hosts. That makes per-credential host allowlists and deny-by-default egress, as in Anthropic's sandbox-runtime proxies ([srt](https://github.com/anthropic-experimental/sandbox-runtime)), more important than the choice of VM. OpenClaw shows the cost of getting the outer layer wrong. Reports put **341 malicious skills among 2,857 on ClawHub**, and a one-click WebSocket-hijacking RCE (CVE-2026-25253) was compounded by an early default binding to `0.0.0.0` ([Barrack.ai](https://blog.barrack.ai/openclaw-security-vulnerabilities-2026/)). Those figures come from secondary sources and conflict, but the lessons hold: review agent-written skills before they are shared workspace-wide, and never expose the control plane on all interfaces.

### Approvals work best as drafts the broker executes

Every framework now offers some form of "pause, serialize, resume": LangGraph `interrupt()`, OpenAI Agents SDK `needsApproval` with a serializable `RunState`, and Claude Agent SDK ask rules ([OpenAI Agents SDK](https://openai.github.io/openai-agents-python/human_in_the_loop); [LangGraph](https://docs.langchain.com/oss/python/langgraph/interrupts)). The reference product's draft model is operationally simpler. A consequential action becomes a stored draft behind Approve/Reject, and "After Approve, I run that exact draft" (reference-product self-description, private notes). For ClawBridge, the broker returns `{status: "draft", draft_id}` to the script immediately and posts the card. On approval, the broker executes the call itself and appends the result to the thread. That avoids holding a container or SDK session open across hour-long waits, avoids the version drift OpenAI warns about for long-paused runs, and keeps the thread append-only for caching. Enforcement has to live in the broker for two reasons. Code-mode calls never surface to `canUseTool`. And the SDK itself warns that "Auto-approved tools never reach `canUseTool`" ([Agent SDK](https://code.claude.com/docs/en/agent-sdk/permissions)). Hooks inside the container don't solve this either, since the agent can edit them (#865).

The details that make approvals trustworthy come mostly from Grok. Approval cards show Allow once, Deny and View details, and **only the requester can respond**. Outbound email and Slack messages are drafted for approval by default. Approvals for unattended work expire after **about 30 minutes**. And an independent review model gates shell, app and computer-use actions, while personal rules can only make it stricter ([xAI](https://docs.x.ai/grok-bot/team-bots); [xAI FAQ](https://docs.x.ai/grok-bot/faq); [xAI security](https://docs.x.ai/grok-bot/security)). Hermes defaults to deny in cron, single-query and unattended modes ([Hermes security](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/security.md)). Codex's experimental "human command checkpoints" cannot be satisfied by session-wide or persistent approvals, and they reject the command if no capable client is connected ([Codex app-server](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)). That is the right model for the reference product's four always-ask classes: spending money, irreversible actions, speaking for someone to outsiders, and messaging anyone outside the current chat. Slack's own Marketplace guideline points the same way: no consequential AI decisions without human review ([Slack](https://docs.slack.dev/slack-marketplace/slack-marketplace-app-guidelines-and-requirements/)). ClawBridge's current approval primitive routes every card to admins and owners ([ClawBridge AI spec](../product-spec.md)). That is right for workspace-level changes and wrong for a requester's own actions.

### Condition gates must run before the container spawns

ClawBridge already inherits the strongest scheduling primitive in the survey, NanoClaw's script gate. The script's last stdout line is `{"wakeAgent": false}` or `{"wakeAgent": true, "data": …}`, with a 30-second timeout and a 1 MB output cap. NanoClaw also **rejects any ungated recurring task that would fire more than four times in 24 hours** ([NanoClaw](https://github.com/nanocoai/nanoclaw/blob/main/docs/scheduled-tasks.md)). ClawBridge's version, however, runs the pre-task script *inside* an already-spawned agent container ([ClawBridge AI spec](../product-spec.md)), so it pays container start-up costs exactly when nothing has happened. The reference product's design point is that "a cheap script … decides whether the model needs to wake at all" (reference-product research, private notes). The gate belongs on the host, in a minimal sandbox with no LLM credentials. Script-only crons, which Hermes calls "no-agent mode", fall out of that design naturally.

Other harnesses contribute guards that ClawBridge can adopt cheaply. Hermes rules that "Cron-run sessions cannot recursively create more cron jobs" ([Hermes cron](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/cron.md)). OpenClaw reschedules overdue jobs on startup instead of replaying them all at once, enforces watchdogs (60 minutes for agent jobs), guards against an interim "on it" being taken as the final result, and has folded heartbeat into ordinary jobs with `activeHours` and `idleOnly` ([OpenClaw cron](https://github.com/openclaw/openclaw/blob/main/docs/automation/cron-jobs/how-it-works.md); [OpenClaw heartbeat](https://github.com/openclaw/openclaw/blob/main/docs/gateway/config-agents/heartbeat-compaction-and-streaming.md)). Grok sets explicit ceilings: 50 routines per Bot, runs at least five minutes apart, 300 runs per hour across routines, and the last 20 runs kept in history. It also triggers routines on Slack mentions, phrases, reactions or any message, and advises that "Slack-triggered routines should not post back without approval" ([xAI](https://docs.x.ai/grok-bot/skills-routines-and-automations)). Grok has no dry-run, so a test run performs real work ([eesel](https://www.eesel.ai/blog/grok-bot)). ClawBridge can do better by routing test runs through the fake-integration broker built for evaluation. Dot's "send only when set conditions are met" reports are the user-facing version of a gate ([getdot changelog](https://www.getdot.ai/changelog)).

### Prompt caching is the largest cost lever, and ClawBridge currently breaks it

The reference product's worked example on Claude Opus 4.8 shows the scale. The thread had a 25k-token stable prefix and 40 calls, sent about 2.17M input tokens in total, and cost **$11.35 uncached versus $2.07 cached** (reference-product research, private notes). The rules behind it are simple. Treat the thread as append-only. Never put a clock in the system prompt; each turn gets a fixed timestamp when it is appended. Deliver mid-thread config changes as new messages. Place breakpoints on the system prompt, the last tool definition and the last two user messages. Compaction then happens *inside* the warm cache: reuse the live thread byte for byte, keep the same tools with `tool_choice: "none"`, and append a compaction instruction. Summarising 60k tokens costs about $0.30 fresh on Opus and about $0.03 in-cache. A delayed signal fires 3 minutes after each reply and is cleared by new activity, so idle threads compact at about 16k tokens while still inside the 5-minute window. The reference product measures **93–96% hit rates on Claude and 88–90% on GPT-5.6** (reference-product research, private notes).

The provider mechanics set the constraints. On Anthropic, 5-minute writes cost 1.25×, 1-hour writes 2×, and reads 0.1× (**0.05× on Opus and Sonnet 5.5**). The minimum cacheable prefix is 512 tokens on current models. Any tool-definition change invalidates everything, and lookback walks at most 20 blocks, so long agent turns need a second breakpoint ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). On OpenAI, GPT-5.6+ offers 30-minute and 12-hour TTLs and routes by a hash of the prefix plus `prompt_cache_key`. Above roughly 15 requests per minute per key, overflow routing causes misses. Changing `tools`, `reasoning.effort` or verbosity breaks the cache, and `allowed_tools` restricts tools without changing the list ([OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)). Codex reportedly keys its cache on the thread ID, and one proxy broke cache continuity by rotating that key ([CLIProxyAPI PR #2374](https://gh.r-mj.com/router-for-me/CLIProxyAPI/pull/2374)). ClawBridge's Claude provider currently sets `systemPrompt.append = memoryContext + instructions`, which puts per-turn recall into the system prompt. Per the spec, that changes the prefix on every query ([ClawBridge AI spec](../product-spec.md)). Per-user MCP tool lists break the cache at the top level for the same reason. One more consequence follows from the rule above: Dot-style `!fast`/`!deep` effort overrides change `effort`/`reasoning.effort`, which invalidates cached messages. The cheaper way to implement them is to hand the turn to a helper running on another model, leaving the main thread's parameters unchanged.

## Evaluation must reward silence and catch leaks

The reference benchmark runs each model as the agent inside simulated copies of real company workspaces, with history, automations and files on disk, and never tells the model it is being tested. Hard state checks ("the right crons in the database", "no forbidden actions") are combined with an LLM judge. Tasks include a sync cron "that finds no new updates, where the right behavior is to update state silently". The published run shows why such a bench is needed and why one run isn't enough (reference-product research, private notes):

| Model | Adjusted pass rate | Avg. cost per task | Behavioural bias |
|---|---|---|---|
| GPT-5.6 Sol | 76% | $33.55 | Under-explores, under-communicates |
| Claude Fable 5 | 76% | $96.35 | Over-explores, over-communicates; 2–3× output tokens |
| GPT-5.6 Terra | 67% | $14.14 | — |
| GPT-5.6 Luna | 62% | $6.44 | — |

The two top models tie on pass rate but differ almost threefold in cost. They also fail in opposite directions, which is the case for per-provider prompt fragments. The reference product tunes model-specific prompt sections against its bench and deletes them when newer models no longer need them (reference-product research, private notes). ClawBridge runs both Claude and Codex, so it can do the same at spawn: a Claude fragment saying that silence is a valid output, and a Codex fragment telling it to dig until sources are covered and prune stale rules. The reference product reports **±2–3 tasks of noise per run**, so every case needs several runs. Public benchmarks don't fill the gap. τ²-bench covers customer service with an LLM-simulated user, and part of what it measures is model-to-model interaction ([sotaverified](https://sotaverified.org/papers/t-2-bench-evaluating-conversational-agents-in)).

Dot contributes two production-side mechanisms that a bench lacks. After every response it reviews the conversation in the background and labels it **Issue, Abandoned or Success-OK**, kept separate from user thumbs. "Abandoned" means a clarifying question went unanswered, which is a quality signal, not a failure. And its golden-answer evaluations live as versioned `evaluations/<id>.yaml` files with a **3% default numeric tolerance**, exported as a GitHub Actions workflow. The accompanying rule: change the expected answer only if the business definition changed; otherwise fix the context ([getdot evaluation](https://docs.getdot.ai/train-dot/evaluation.md); [getdot maintenance](https://docs.getdot.ai/train-dot/maintaining-dot.md)). Code mode makes the bench cheap to build. Every integration call already passes through the broker, so swapping in recorded or fake backends gives fixtures, dry-runs and policy-table tests from one mechanism.

## Conclusion

The research changes where the agent's quality work belongs: in the host, not the prompt. Every hard-won behaviour in the comparators either is a host-enforced invariant or fails without one. Grok's never-lend-access rule, Dot's proposal diffs, the reference product's private-stays-private rule, NanoClaw's credentials-never-enter-the-container rule and Codex's non-bypassable checkpoints are the first kind. Hermes's "I told it to remember" failure, NanoClaw's agent-editable hooks and OpenClaw's off-by-default sandbox are the second. ClawBridge's container-per-agent design and existing host credential proxy put it closer to that model than OpenClaw or Hermes, which are fighting single-tenant architectures. What ClawBridge lacks is a single host broker that owns identity, scope, credentials, approvals, gates and audit at once. Building that one component unlocks most of the P0 and P1 list together, including a cheap evaluation harness.

The less obvious implication is that Slack has already made the agent's distribution decision. Since the 2025–2026 platform changes, self-hosting is no longer just a privacy feature. It is the cheapest legitimate way to get full history rate limits, Real-time Search and the Slack MCP server without a Marketplace review. That should shape ClawBridge's packaging: a polished manifest-and-provisioning flow per customer workspace matters more to best-in-class Slack quality than any single model or prompt improvement.
